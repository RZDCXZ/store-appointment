# 茸光宠物洗护预约与排班系统

Status: ready-for-agent

## Problem Statement

单门店宠物洗护业务依赖电话和聊天确认预约时，顾客无法自行判断某项服务、某只宠物和某位员工真正可用的时间，店长也很难同时协调营业时间、员工技能、班次、休息、停班和已有预约。结果是沟通往返、撞单、临时请假后遗漏受影响预约、到店核销混乱，以及宠物资料和服务历史分散。

本项目还需要解决一个作品集层面的可信度问题：普通表单式预约 Demo 无法证明开发者处理过真实的时间边界、并发冲突、状态历史、隐私权限和通知失败。项目必须在不正式上线、不依赖真实微信密钥、支付或生产基础设施的前提下，于本地完整运行，并以可重复测试证明关键业务规则成立。

## Solution

建设上海虚构品牌“茸光宠物洗护”的单门店预约系统，包括真实原生微信小程序顾客端，以及员工与店长共享的响应式 Web 后台。顾客先选择宠物、主要服务和增项，系统再根据服务规格、员工技能与已发布排班计算确定的可约时段；创建成功时立即确认并分配具体员工。后台围绕今日工作、预约日历、排班与容量变更、履约、顾客档案、通知异常、审计和经营看板形成同一业务闭环。

系统以 PostgreSQL 作为并发一致性的最终防线，保留预约原计划、快照、状态历史和实际占用。微信身份和订阅消息使用明确标注的本地模拟实现；确定性种子、可注入演示时钟和数据重置保证相同场景可以反复验证。项目公开源码，只承诺本地运行，不把演示实现表述为可直接生产上线的产品。

## User Stories

### 顾客与宠物档案

1. As a 顾客, I want to 查看门店品牌、地址、营业时间和联系方式, so that 我能判断这家门店是否适合我的宠物。
2. As a 顾客, I want to 浏览犬猫洗护服务及适用范围, so that 我能理解门店提供什么。
3. As a 顾客, I want to 看到服务规格对应的确定价格和服务时长, so that 我能在预约前做出明确选择。
4. As a 顾客, I want to 创建自己的宠物档案, so that 后续预约不必重复填写基础资料。
5. As a 顾客, I want to 为宠物填写名称、种类和当前体重, so that 系统能自动确定体型和服务规格。
6. As a 顾客, I want to 选填宠物品种、性别、出生日期、毛发类型和照片, so that 门店获得更完整的履约背景。
7. As a 顾客, I want to 添加怕吹风、对陌生犬敏感等护理标签, so that 员工能提前注意安全与偏好。
8. As a 顾客, I want to 填写自由文本护理注意事项, so that 结构化标签之外的重要信息不会遗漏。
9. As a 顾客, I want to 修改宠物当前资料, so that 下次预约使用最新信息。
10. As a 顾客, I want to 归档没有未来预约的宠物, so that 它不再出现在新预约选择中但历史仍然保留。
11. As a 顾客, I want to 恢复归档宠物, so that 我可以再次为它预约。
12. As a 顾客, I want to 在宠物仍有未来预约时被阻止归档, so that 预约不会失去服务对象。
13. As a 顾客, I want to 在首次预约前阅读并同意当前隐私说明, so that 我的同意是明确且可追踪的。
14. As a 顾客, I want to 在隐私说明版本更新后重新确认, so that 新版本不会被默认视为已同意。
15. As a 本地体验者, I want to 在三个有明确故事的演示顾客之间切换, so that 我能快速体验不同预约和历史状态。

### 顾客预约

16. As a 顾客, I want to 按“宠物 → 主要服务 → 增项 → 员工偏好 → 日期与时段”完成预约, so that 每一步都建立在已知条件上。
17. As a 顾客, I want to 每笔预约只选择一只宠物, so that 员工、状态、价格和服务记录保持明确。
18. As a 顾客, I want to 选择一个主要服务和若干兼容增项, so that 我能在一次连续服务中完成所需护理。
19. As a 顾客, I want to 增项自动计入价格、服务时长和技能要求, so that 结果不是到提交时才变化。
20. As a 顾客, I want to 指定喜欢的员工, so that 熟客偏好能够被满足。
21. As a 顾客, I want to 选择“最快可约”而不指定员工, so that 系统为我找到最早的确定安排。
22. As a 顾客, I want to 在预约成功时立即知道具体员工, so that 不会得到一个尚待门店分配的容量承诺。
23. As a 顾客, I want to 浏览未来十四个上海自然日的日期条, so that 我能快速定位可预约日期。
24. As a 顾客, I want to 只看到从当前时间两小时后开始的候选时段, so that 门店有合理准备时间。
25. As a 顾客, I want to 看到每三十分钟生成的候选开始时间, so that 时间选择简单且一致。
26. As a 顾客, I want to 区分闭店、无合格员工和已约满, so that 我知道某天不可预约的真实原因。
27. As a 顾客, I want to 看到服务与十五分钟周转都能完整覆盖的时段, so that 门店不会在结束边界制造冲突。
28. As a 顾客, I want to 在确认页复核宠物、服务、增项、员工、时间、价格和时长, so that 提交前没有歧义。
29. As a 顾客, I want to 提交后立即获得已确认预约, so that 无需等待门店再次接单。
30. As a 顾客, I want to 在时段刚被他人抢走时得到明确冲突提示和相近建议, so that 我无需重新填写宠物与服务。
31. As a 顾客, I want to 重复提交同一操作时获得首次结果, so that 网络重试不会创建重复预约。
32. As a 顾客, I want to 同时为不同宠物预约不同员工, so that 两只宠物可以同时接受服务。
33. As a 顾客, I want to 被阻止为同一宠物创建重叠服务, so that 一只宠物不会被安排在两个地方。
34. As a 顾客, I want to 查看自己的未来和历史预约, so that 我能掌握全部服务安排。
35. As a 顾客, I want to 查看预约的宠物、服务快照、员工、计划时间、状态和价格, so that 后续配置变化不会改写我的承诺。
36. As a 顾客, I want to 在已完成预约中看到实际完成时间, so that 服务历史反映真实履约。
37. As a 顾客, I want to 看不到门店内部服务记录, so that 内部履约信息不会被当作对客内容。
38. As a 顾客, I want to 在开始前至少十二小时自行取消, so that 无需联系门店即可释放时段。
39. As a 顾客, I want to 在恰好提前十二小时时仍可取消或改期, so that 截止点规则可预测。
40. As a 顾客, I want to 在截止时间后得到联系门店的明确说明, so that 预约不会被静默删除。
41. As a 顾客, I want to 在允许时间内原子改期, so that 新时段失败时原安排仍然保留。
42. As a 顾客, I want to 在改期后获得新的核销码, so that 旧安排的凭证不能继续使用。
43. As a 顾客, I want to 在修改宠物或服务内容时被引导取消并重新预约, so that 顾客端不会产生复杂且不透明的重新定价。
44. As a 顾客, I want to 在预约详情中看到六位核销码, so that 到店后能向员工提供简单稳定的凭证。
45. As a 顾客, I want to 在核销窗口未开始时看到明确提示, so that 提前到店不会被误认为服务已经开始。
46. As a 顾客, I want to 在消息页查看预约确认、改期、取消和提醒消息, so that 模拟通知仍然可验证。
47. As a 顾客, I want to 导出自己的结构化 JSON 数据, so that 我能查看系统保存了哪些资料。
48. As a 顾客, I want to 在处理完未来预约后请求删除资料, so that 个人和宠物信息被匿名化而非继续公开可识别。
49. As a 顾客, I want to 在删除前知道哪些历史事实会匿名保留, so that 演示规则不会伪装成法律结论。

### 员工履约

50. As an 员工, I want to 使用自己的预置账号登录后台, so that 我的权限由服务端身份决定。
51. As an 员工, I want to 首先看到“我的今日预约”, so that 我能在手机或桌面快速开始工作。
52. As an 员工, I want to 看到下一位宠物、迟到待处理、待核销和待完成事项, so that 高优先级履约动作不会遗漏。
53. As an 员工, I want to 只能查看分配给自己的预约, so that 其他员工和顾客数据不被越权读取。
54. As an 员工, I want to 查看履约所需的顾客姓名、脱敏手机号、宠物档案和护理注意事项, so that 我能完成服务而不过度暴露资料。
55. As an 员工, I want to 主动揭示完整手机号并留下审计记录, so that 必要联系与敏感访问可以同时成立。
56. As an 员工, I want to 查看该宠物的历史服务记录, so that 我能了解以往护理情况。
57. As an 员工, I want to 输入有效核销码确认到店, so that 到店事实与预约绑定。
58. As an 员工, I want to 重复提交同一核销时获得原结果, so that 重试不会产生重复状态变化。
59. As an 员工, I want to 在预约开始超过十五分钟后填写原因并手动迟到核销, so that 真实到店顾客仍可继续服务。
60. As an 员工, I want to 在开始超过十五分钟且仍未到店时标记爽约, so that 系统不靠时间自动猜测履约结果。
61. As an 员工, I want to 必须先核销且不早于计划开始时间才能完成服务, so that 完成记录不能提前伪造。
62. As an 员工, I want to 完成服务时自动生成结构化服务记录, so that 不必强制填写无意义文字。
63. As an 员工, I want to 选填护理标签和内部文字, so that 有价值的服务信息可以沉淀。
64. As an 员工, I want to 在宠物应激等情况下终止已到店服务并填写原因, so that 该结果不会伪装成完成、取消或爽约。
65. As an 员工, I want to 在服务记录错误时追加说明而非覆盖原文, so that 修改过程保持可追踪。
66. As an 员工, I want to 无法取消、改期或更换不属于自己职责的预约, so that 门店承诺只由店长处理。

### 店长预约与容量管理

67. As a 店长, I want to 登录后先看到今日工作台, so that 待处理停班、通知失败和迟到事项优先于长期图表。
68. As a 店长, I want to 按员工分列查看日时间轴, so that 我能直观看到班次、休息、停班和预约占用。
69. As a 店长, I want to 查看周负载摘要, so that 我能快速定位高低负载日期。
70. As a 店长, I want to 搜索和筛选预约列表, so that 异常与历史预约容易定位。
71. As a 店长, I want to 代录电话、聊天或到店预约, so that 所有渠道都进入同一冲突校验。
72. As a 店长, I want to 为新顾客代录最小资料和线下隐私同意来源, so that 代客预约不会绕过隐私事实。
73. As a 店长, I want to 为临近时段代客预约, so that 我可以绕过顾客端两小时提前量但不制造资源冲突。
74. As a 店长, I want to 在核销前纠正宠物体重、服务规格或增项, so that 填错信息可以修复。
75. As a 店长, I want to 只有在技能与连续容量仍满足时保存纠正, so that 价格和时长变化不会覆盖下一笔预约。
76. As a 店长, I want to 通过显式改期面板查看可用建议, so that 改期不是一次不透明的日历拖拽。
77. As a 店长, I want to 改期时填写原因并保留原员工与时段, so that 顾客沟通和审计都完整。
78. As a 店长, I want to 在核销前填写原因取消预约, so that 门店取消与到店后的服务终止保持不同含义。
79. As a 店长, I want to 在超出核销码窗口后手动确认迟到到店, so that 特殊情况能够处理且留痕。
80. As a 店长, I want to 创建和停用主要服务、增项与服务规格, so that 门店目录可以维护而不破坏历史快照。
81. As a 店长, I want to 修改价格、服务时长和适用范围只影响新预约, so that 已有顾客承诺不会静默变化。
82. As a 店长, I want to 创建、停用员工账号并分配员工技能, so that 可预约人员和权限保持一致。
83. As a 店长, I want to 在停用员工前处理其未来预约, so that 顾客不会留下无员工承接的预约。
84. As a 店长, I want to 维护每周排班模板, so that 常规班次不必逐日重复录入。
85. As a 店长, I want to 从模板生成未来十四天排班草稿, so that 排班可以预览后再发布。
86. As a 店长, I want to 发布具体日期的班次, so that 只有已确认容量才向顾客开放。
87. As a 店长, I want to 为具体日期设置调班、加班或休息例外, so that 周模板不会限制实际经营。
88. As a 店长, I want to 创建员工停班, so that 突发不可用立即阻止新预约。
89. As a 店长, I want to 创建门店临时闭店, so that 整体停止营业不需要伪装成全员停班。
90. As a 店长, I want to 在容量变更影响预约时先看到完整影响列表, so that 系统不会自动移动或取消顾客安排。
91. As a 店长, I want to 对每笔受影响预约选择同时间换员工、改期或取消, so that 处理结果符合真实沟通。
92. As a 店长, I want to 在所有影响处理完成后使停班或闭店正式生效, so that 容量状态与预约事实一致。
93. As a 店长, I want to 撤销尚未完成处理的停班, so that 错误操作可以恢复原容量。
94. As a 店长, I want to 不能强制创建员工或宠物时间重叠, so that 管理权限不是绕过一致性的后门。

### 通知、顾客档案与审计

95. As a 店长, I want to 查看通知任务的待发送、已发送、失败和重试状态, so that 消息失败不会被预约成功提示掩盖。
96. As a 店长, I want to 查看每次模拟发送尝试, so that 自动重试过程可以解释。
97. As a 店长, I want to 在三次自动失败后人工重试通知, so that 最终失败能够进入工作台处理。
98. As a 店长, I want to 注入一次模拟通知失败, so that 失败与重试路径可以稳定演示。
99. As a 店长, I want to 在演示模式推进时间, so that 不必真实等待二十四小时即可触发提醒。
100. As a 店长, I want to 看到推进演示时间的审计记录, so that 测试动作不会伪装成自然时间经过。
101. As a 店长, I want to 查看顾客、宠物和历史服务, so that 分散资料集中在同一履约上下文中。
102. As a 店长, I want to 导出筛选后的预约 CSV, so that 运营数据可以在本地进一步分析。
103. As a 店长, I want to 导出顾客与宠物 JSON, so that 层级档案保持结构化。
104. As a 店长, I want to 查看预约、配置、权限、手机号揭示、导出、删除和通知重试的审计记录, so that 重要写操作与敏感读取可追溯。
105. As a 店长, I want to 无法修改或删除审计记录, so that 日志不是可被管理员重写的装饰。

### 经营看板

106. As a 店长, I want to 默认查看最近三十天并切换七、三十和九十天, so that 我能观察不同周期的经营情况。
107. As a 店长, I want to 与前一等长周期比较, so that 当前变化有明确参照。
108. As a 店长, I want to 查看服务工时利用率及公式说明, so that 指标不会被误解为简单预约占用率。
109. As a 店长, I want to 查看已完成服务标价并看到“非实收金额”说明, so that 没有支付闭环时不虚构营收。
110. As a 店长, I want to 分别查看取消、爽约和服务终止, so that 不同异常不会混成一个不可行动的数字。
111. As a 店长, I want to 查看九十天复访顾客占比, so that 顾客回访可以从完成记录计算而不是被称为复购。
112. As a 店长, I want to 在图表之外看到数值和文本说明, so that 状态与趋势不只依赖颜色表达。

### 本地演示与工程可信度

113. As a 代码审阅者, I want to 用一个命令启动数据库、迁移、种子、API 和后台, so that 本地验证成本可控。
114. As a 代码审阅者, I want to 按说明用自己的测试 AppID 导入原生小程序, so that 仓库不共享任何微信秘密。
115. As a 代码审阅者, I want to 看到明确的演示认证、模拟消息和本地文件标识, so that 案例不会伪装成生产系统。
116. As a 代码审阅者, I want to 使用固定 DEMO_NOW 重置数据, so that 日期相关结果可以重复验证。
117. As a 代码审阅者, I want to 连续重置三次得到相同时段、状态和统计, so that 演示不依赖随机运气。
118. As a 代码审阅者, I want to 在种子数据中看到过去一百八十天历史和未来十四天安排, so that 趋势与前期比较都有可信数据。
119. As a 代码审阅者, I want to 固定看到待处理停班、通知失败、迟到、待核销和待完成场景, so that 异常流程可以直接验证。
120. As a 代码审阅者, I want to 并发争抢同一时段二十次时只成功一次, so that 数据库约束而非页面按钮保证不撞单。
121. As a 代码审阅者, I want to 阅读 OpenAPI、领域语言和架构决策, so that 业务规则与代码边界容易理解。
122. As a 外部贡献者, I want to 在普通 Linux CI 中运行主要检查, so that 不配置微信桌面环境也能验证核心正确性。
123. As a 维护者, I want to 在本机手动运行少量微信开发者工具黄金流程, so that 原生小程序页面集成仍有真实验证。
124. As a 店长, I want to 仅在演示模式二次确认后重置数据, so that 普通操作不会误清除本地数据。
125. As a 使用者, I want to 重置后所有旧会话失效, so that 会话不会引用重建前身份与数据。
126. As a 使用者, I want to 在查询失败时保留已显示数据并明确重试, so that 短暂故障不会把界面伪装成空状态。
127. As a 使用者, I want to 区分认证过期、无权限、校验失败、时段冲突和服务器故障, so that 我能采取正确下一步。
128. As a 键盘使用者, I want to 在后台看到可见焦点、关联表单错误和可操作控件, so that 基础操作不依赖鼠标和颜色。

## Implementation Decisions

### 产品与领域边界

- 项目是单门店宠物洗护作品集案例，不是跨行业模板、多租户 SaaS 或正式上线产品。
- 使用唯一领域语言：顾客、员工、店长、宠物、预约、主要服务、增项、服务规格、已发布排班、停班、临时闭店、到店核销、服务终止等；实现不得重新引入“订单”“商家改期”“会员”等被排除同义词。
- 顾客端是原生微信小程序；员工和店长共用响应式 Web 后台。后台按角色限制导航、操作与数据范围，所有权限由服务端执行。
- 产品仅支持简体中文、中国大陆手机号、人民币分、二十四小时时间和 `Asia/Shanghai` 业务时区。
- 顾客端底部导航为首页、预约记录、消息、我的；后台店长导航为工作台、预约、排班、服务、顾客、经营、系统。
- 店长复杂页面以本机稳定版 Chrome 的桌面宽度为验收环境；员工工作台、登录和本人预约支持约 390px 手机宽度。
- 品牌为“茸光宠物洗护”，采用奶油底色、鼠尾草绿和珊瑚强调色的单一浅色主题。基础组件可以复用 shadcn/ui，但工作台、日历和信息层级必须体现领域设计，不保留默认模板感。

### 服务目录与人员

- 三个主要服务：犬基础洗护、犬造型美容、猫咪洗护。三个增项：修甲护理、除废毛护理、口腔清洁。
- 犬基础洗护的小／中／大型规格分别为 ¥128／60 分钟、¥168／90 分钟、¥228／120 分钟。
- 犬造型美容的小／中／大型规格分别为 ¥228／120 分钟、¥328／150 分钟、¥458／180 分钟。
- 猫咪洗护的小／中／大型规格分别为 ¥168／90 分钟、¥218／120 分钟、¥288／150 分钟。
- 修甲护理为 ¥30／15 分钟，口腔清洁为 ¥35／15 分钟；除废毛护理的小／中／大型规格分别为 ¥60／30 分钟、¥90／45 分钟、¥120／60 分钟。
- 小型体型为不超过 10kg，中型为超过 10kg 且不超过 25kg，大型为超过 25kg。预约保存当时体重、体型、价格和时长快照。
- 林夏掌握犬基础洗护、犬造型美容和全部增项；陈嘉掌握犬基础洗护、猫咪洗护、修甲与除废毛；周宁掌握猫咪洗护、修甲与口腔清洁；赵航掌握犬基础洗护、犬造型美容、修甲与口腔清洁。
- 员工必须同时覆盖主要服务及全部增项技能。一笔预约始终由一名员工连续完成。
- 已被历史引用的服务、增项和员工只能停用，不能物理删除。服务变更只影响新预约。

### 营业、排班与可约时段

- 门店周二至周日 09:30–19:00 营业，周一闭店。
- 林夏周二至周六 09:30–18:00，13:00–14:00 休息；陈嘉周三至周日 10:30–19:00，14:00–15:00 休息；周宁周二、周四至周日 09:30–18:00，12:30–13:30 休息；赵航周二至周六 10:30–19:00，14:30–15:30 休息。
- 每周排班模板只生成草稿；只有未来十四个自然日的已发布排班形成可预约容量。具体日期可以设置调班、加班或休息例外。
- 候选开始时间每三十分钟生成一次。顾客窗口包含上海本地今天至第十三天，最早时段为当前时间加两小时后向上取整到下一候选点。
- 所有时间区间采用左闭右开 `[start, end)` 语义。服务及十五分钟周转必须完整落在门店营业、员工班次和可用区间内，不得跨越休息、停班或闭店。
- 首版唯一排他容量是员工；不建模浴池、设备、房间或多阶段流水线。同一员工的实际占用不能重叠，同一宠物的服务时间不能重叠。
- “最快可约”先取最早可用开始时间；同一时间有多人可用时，选择当天已占用计划服务分钟数最少者，再按固定员工编号打破平局。
- 浏览和确认不产生临时占位。创建时重新校验；冲突时保留顾客选择并返回相近建议。
- 店长代客预约可以绕过两小时提前量，但不能绕过营业、排班、技能、冲突、停班、闭店或未来十四天已发布窗口。

### 预约生命周期与历史

- 状态机为 `CONFIRMED → CHECKED_IN → COMPLETED | TERMINATED`，以及 `CONFIRMED → CANCELLED | NO_SHOW`。UI 分别显示已确认、已到店、已完成、已终止、已取消、已爽约。
- 迟到待处理是时间派生的工作台提醒；改期是历史事件；二者不是长期预约状态。
- 顾客在预约开始前至少十二小时可以取消或改期，恰好十二小时允许操作。截止后只能联系门店。
- 顾客或店长改期保留同一预约身份；事务先锁定新容量，再释放旧占用并追加原安排、操作人和原因。失败时原安排保持不变。
- 店长在核销前可以纠正体重、服务规格或增项，但必须重新计算价格、时长、技能和容量并追加历史。更换宠物或完全不同的主要服务使用取消后新建。
- 店长只可在到店核销前取消并要求原因；到店后只能完成或服务终止。
- 原计划区间、服务快照和状态历史永久保留。独立实际占用参与冲突约束：取消清空未发生占用，爽约在人工处理时释放后续容量，提前完成或服务终止在实际结束后保留十五分钟周转。
- 完成必须先到店核销且当前时间不早于计划开始；允许早于预计结束完成。完成生成结构化服务记录，护理标签与内部文字选填。
- 服务记录不能覆盖或删除，只能由员工或店长追加带作者与时间的更正说明。

### 核销、爽约与通知

- 核销码为六位一次性凭证，只保存不可逆摘要。改期轮换，取消后失效，首次核销后不能再次改变状态。
- 正常核销窗口为开始前三十分钟至开始后十五分钟。窗口前不能提前核销；窗口后分配员工或店长填写原因手动核销。
- 开始超过十五分钟且仍为已确认时，分配员工或店长可以人工标记爽约。系统不自动判定爽约，也不据此自动处罚顾客。
- 预约确认、顾客或店长改期、顾客或店长取消、停班影响处理结果，以及开始前二十四小时提醒产生通知任务。创建时已经不足二十四小时的不补发提醒。
- 业务变更与通知 outbox 在同一 PostgreSQL 事务中提交。通知失败不回滚预约事实。
- 模拟微信通道自动短退避重试三次，随后进入需人工重试。每次尝试可查看，顾客消息保持幂等。
- 演示模式允许店长推进可注入时钟以触发到期提醒，该动作写入审计记录。

### 容量变更流程

- 修改营业时间、已发布班次或休息，创建停班或临时闭店，只要影响已有预约，就先进入待处理状态并立即阻止该区间新预约。
- 店长逐笔选择同时间换员工、改期或取消；系统提供可用建议但不自动决定。全部受影响预约处理完毕后容量变更才生效。
- 待处理停班可以撤销并恢复原容量。任何角色都不能强制创建重叠安排。

### 身份、权限、隐私与审计

- 本地后台预置一个店长和四个员工账号，使用文档公开的统一演示密码；密码仍使用安全哈希。后台使用 HttpOnly、SameSite Cookie 会话，并保护写请求来源或 CSRF。
- 小程序提供三个快捷演示顾客，服务端签发短期 Bearer 会话。前端不能通过传角色字段声明身份。
- 员工只可操作分配给自己的预约；可见顾客姓名、脱敏手机号、宠物档案、护理注意事项和该宠物历史服务记录。完整手机号揭示必须主动触发并审计。
- 员工不能取消、改期、更换员工、手动超越容量或管理门店配置。店长固定为一个，不实现角色转让或多管理员组织系统。
- 顾客必填姓名和中国大陆手机号，不收集地址、身份证、邮箱或微信号。
- 隐私同意保存版本、时间、顾客和来源；代客预约保存店长及线下确认来源。
- 顾客数据导出为结构化 JSON。删除前必须处理未来预约，之后匿名化顾客、宠物、护理资料和身份关联，但保留不含身份信息的预约历史、经营统计和删除审计事实。
- 审计覆盖预约变化、服务和排班配置、停班与闭店、账号权限、手机号揭示、导出、删除、通知重试和演示时间推进。数据库触发器拒绝审计记录更新与删除。
- 审计规则是作品集演示规则，不声明满足具体司法辖区的法定保留期限。

### 看板与导出

- 店长首页先显示待处理停班、通知失败、迟到待处理，以及今日时间线与状态汇总。长期经营数据位于独立看板。
- 看板默认最近三十天，可切换七、三十、九十天，并和前一个等长周期比较。
- 服务工时利用率等于已完成预约的计划服务分钟数，除以员工已发布排班扣除休息与生效停班后的分钟数；不含取消、爽约、终止和周转。
- 已完成服务标价汇总已完成预约价格快照，必须标记为非实收金额。
- 取消按最终计划开始日统计，以全部预约为分母；爽约以未取消预约为分母；服务终止单列数量与比例。
- 九十天复访顾客占比等于九十天内至少完成两次服务的顾客数，除以至少完成一次服务的顾客数。
- 预约运营数据按筛选条件导出 CSV；顾客与宠物档案导出 JSON；每次导出写入审计。

### 架构与基础设施

- 使用 pnpm workspace 与 Turborepo 的 TypeScript 单仓库；应用边界为原生微信小程序、React/Vite 后台和 NestJS/Fastify API。
- 服务端为模块化单体，按身份、顾客与宠物、服务目录、排班与容量、预约与履约、通知、审计、经营和演示支持划分模块，共享一个 PostgreSQL。
- API 使用 REST/OpenAPI。创建、改期、取消、核销等命令要求幂等键；同一身份和幂等键返回首次结果。
- API 使用稳定业务错误码区分无权限、同意缺失、窗口外、截止时间已过、状态转换非法、时段冲突、容量变更影响、核销窗口和普通服务器故障。
- 后台通过 SSE 接收“需要刷新”的事件，断线重连后重新拉取当前事实；SSE 事件不是业务事实来源。
- 数据层使用 PostgreSQL 与 Drizzle ORM。员工和宠物有效占用使用范围排除约束；Drizzle 无法表达的约束、不可变审计触发器等使用显式 SQL migration。
- 所有 schema 变化只通过 migration；应用启动不得偷偷同步 schema。种子、迁移和重置是独立步骤。
- 金额以人民币分保存；真实时刻保存 UTC 时间戳，排班规则保存上海本地日期与时间并显式绑定业务时区；所有“现在”来自可注入时钟。
- 种子图片随仓库提供；本地上传保存到被忽略的数据目录，校验文件类型和大小。重置恢复种子状态。该存储不被描述为生产对象存储。
- Docker Compose 仅运行锁定小版本的 PostgreSQL；Node 应用运行在宿主机。默认命令负责健康检查、迁移、重置种子并并行启动 API 与后台。
- 微信开发者工具单独导入小程序，使用者提供自己的测试 AppID。真实 AppID 私有配置、AppSecret、上传密钥、数据库数据、上传文件和环境文件不得提交。
- 不依赖旧版无 AppID 模式。开发者工具可在开发期关闭域名校验；真机使用同一局域网内电脑 IP，而不是 `localhost`。
- 真实微信登录和订阅消息只定义适配器接口与接入条件，首版不实现真实适配器。
- 代码标识、数据库与 API 使用英文；用户界面、README 主文档、领域文档和规格使用简体中文。

### 演示数据与完成标准

- 种子包含二十名顾客、约二十八只宠物、过去一百八十天约二百四十笔终态预约，以及当前和未来十四天约四十笔预约。
- 三个快捷顾客分别覆盖正常预约、已有未来预约、取消或爽约历史。其余顾客作为背景数据。
- 重置后固定存在一个待处理停班、一个最终失败通知、一个迟到待处理、一个待核销、一个已到店待完成，以及一个可供并发争抢的唯一时段。
- 支持 `DEMO_NOW` 固定演示时间；启用时所有界面明确标识演示模式。店长界面重置需要二次确认，CLI 也提供明确命令；重置使全部旧会话失效。
- 最终完成要求所有规格场景通过、CI 全绿、从空数据库连续重置并跑通三次，且不存在主流程阻断、越权、时间冲突、状态错误或无法重置问题。
- 不设正式性能 SLO、跨浏览器矩阵、部署、备份或生产监控验收。实现仍应避免肉眼可见卡顿和明显 N+1，但不单独制作性能报告。

## Testing Decisions

- 好测试验证调用者可观察行为，不锁定内部类、私有函数、SQL 形状或组件实现。重构内部模块时，只要相同输入仍产生相同状态、错误、通知、审计与查询结果，测试应继续通过。
- 主要测试接缝是带真实 PostgreSQL 的 HTTP API。预约、排班、容量变更、生命周期、权限、通知 outbox、审计和看板尽量从这一最高接缝验证，避免在控制器、服务、仓储各复制一套 mock 测试。
- 纯领域测试只覆盖组合数量较大的确定性规则：体型边界、服务规格、三十分钟候选点、两小时取整、十四日窗口、十二小时截止、左闭右开区间、技能过滤、最快可约平局、周转和指标公式。
- PostgreSQL 集成测试使用真实数据库而非内存替身，验证范围排除约束、员工冲突、宠物冲突、原子改期、容量释放、不可变审计触发器、migration 和事务 outbox。
- 并发验收对同一时段发起二十个创建请求，只允许一个成功；其他请求返回稳定冲突错误与新建议。相同幂等键的重复请求返回首次结果，不算新的竞争者。
- API 权限测试从顾客、分配员工、其他员工和店长四种身份验证读取与写入边界，包括完整手机号揭示、顾客数据导出／删除和审计不可修改。
- API 状态机测试覆盖每个允许与拒绝的转换，特别是过早完成、核销前终止、核销后取消、十五分钟爽约边界、迟到手动核销和重复命令。
- 容量变更测试覆盖班次、休息、停班、临时闭店、待处理阻断、逐笔处理、撤销和最终生效；验证系统从不自动移动预约。
- 通知测试验证业务事务与 outbox 原子提交、三次自动失败、人工重试、顾客消息幂等、通知失败不回滚预约，以及演示时钟触发二十四小时提醒。
- 后台使用 Playwright 只覆盖高价值流程：店长今日工作台、按员工日历、受影响预约处理、员工核销与完成、通知失败重试、权限失败和演示重置。视觉细节不通过脆弱的全页快照锁死。
- 小程序在普通 CI 中运行 TypeScript 逻辑测试和 `miniprogram-simulate` 自定义组件测试，覆盖日期选择、预约卡片、状态标签、核销码和错误映射。
- 小程序本地手动任务使用 `miniprogram-automator` 保留三至五条黄金流程：切换顾客、创建宠物、查询并创建预约、改期或取消、查看核销码。该任务依赖微信开发者工具与测试 AppID，不作为外部 PR 的强制门禁。
- 真机验收至少在一台手机完成局域网请求、主流程、键盘、滚动、安全区和页面切换检查，并记录验证过的微信、基础库和开发者工具版本。
- 每个核心页面至少验证加载、空数据、可重试错误、无权限和字段级表单错误；查询失败保留已有数据，写失败不显示假成功。
- GitHub Actions 必跑格式、Lint、类型检查、领域测试、小程序组件测试、API 权限测试、真实 PostgreSQL 集成测试、后台关键 E2E 和生产构建。
- 当前代码库没有既有测试先例；本规格自身及 ADR 是首批约束。实现时应优先形成上述单一高层 API 接缝，不为追求覆盖率拆出大量内部测试缝。

## Out of Scope

- 正式上线、微信审核发布、生产域名、HTTPS 证书、生产扩缩容、监控告警、备份恢复和灾难演练。
- 真实微信登录、`code2Session`、真实订阅消息下发、短信、地图和第三方日历集成。
- 真实支付、订金、退款、储值、预付卡、对账、发票和资金合规。
- 多门店、多商户、多租户、跨店员工、白标主题和跨行业配置。
- H5 顾客端、其他小程序平台、Taro、uni-app 和维护两套顾客客户端。
- 浴池、设备、房间容量，多阶段流水线，跨天寄养和日托。
- 医疗诊断、治疗建议、疫苗、处方和受监管医疗记录。
- 套餐、次卡、优惠券、积分、会员等级、等候名单、自动空位通知、团购、分销和营销自动化。
- 顾客评分、公开评论、投诉工单、员工提成、库存消耗和收银系统。
- 自动处罚爽约顾客、模拟订金门槛或复杂申诉流程。
- 自动顺延超时服务后的其他顾客预约；超时只记录实际完成时间和内部说明。
- 暗色模式、多主题、多语言、多币种和完整跨浏览器兼容矩阵。
- 针对公网的 WAF、验证码、入侵检测和生产限流。基本身份、输入、CSRF、上传和日志安全仍属于范围。
- 正式性能 SLO、专项压测报告和跨设备实验室。明显卡顿与明显 N+1 仍应在正常开发中修正。
- 当前阶段的作品集截图、录屏、个人网站案例文章和营销文案；产品完成后另行规划。

## Further Notes

- 本规格受根领域词汇表和 ADR-0001 至 ADR-0010 约束。若实现需要改变已记录的领域语言或难逆转取舍，应先更新相应领域文档或新增 ADR，而不是静默偏离。
- 项目采用成果导向，不设开发时间盒。成果导向不表示无限扩张；新想法记录为延后项，只有发现领域矛盾或无法满足既定验收时才调整首版。
- 建议按纵向切片实施：工程骨架与规则；最小预约双端闭环；履约与通知；排班和容量变更；隐私权限审计；看板、种子、异常和整体精修。每个切片必须保持可运行并包含相应测试。
