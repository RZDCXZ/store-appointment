# 27 — 经营看板

**What to build:** 让店长用明确公式理解服务工时、已完成服务标价、异常结果和顾客复访，而不把没有支付闭环的数据称为营收。

**Blocked by:** 15 — 完成服务、服务终止与追加说明; 23 — 逐笔处理受影响预约; 25 — 店长顾客与宠物档案及导出.

**Status:** ready-for-human

- [x] MG-17 经营看板使用独立后台路由，可直接访问、刷新和恢复所选周期。
- [x] 默认显示最近三十天，并可切换七、三十、九十天，与前一个等长周期比较。
- [x] 服务工时利用率严格使用已完成预约计划服务分钟数除以排班扣除休息和生效停班后的分钟数，不含周转、取消、爽约或终止。
- [x] 已完成服务标价按预约价格快照汇总，并在数值旁持续显示“非实收金额”。
- [x] 取消率按全部预约、爽约率按未取消预约计算，服务终止单独显示数量和比例。
- [x] 九十天复访顾客占比只计算至少完成两次服务的顾客，并明确分母定义。
- [x] 所有指标提供精确数值、公式和趋势文字，状态与趋势不只靠红绿颜色表达。
- [x] 时间周期以预约最终计划开始日和上海业务日期归属，日期边界有确定测试。
- [x] 员工不能访问经营看板或指标 API。
- [x] 领域公式测试、API 测试和 UI 测试在固定数据下得到唯一结果，并覆盖空周期与局部查询失败。

## Comments

### 2026-08-19 — implementation

- 设计稿页面 → 实际路由：MG-17 经营看板 → `/manager/business?period=:period`。页面使用独立路由模块，默认 30 天，支持 7／30／90 天 URL 状态恢复，并通过 Playwright 验证直接访问、刷新、周期切换、导出和员工角色边界。
- 新增店长经营指标、每日趋势和 CSV 导出 API；同一响应在 PostgreSQL 可重复读快照内汇总，两个只读响应携带当前周期事实版本，前端发现跨响应版本不一致时隐藏趋势并提供共同重试。CSV 沿用当前周期筛选并写入 `data_exported` 审计事实。
- 领域计算按最终计划开始日和上海业务日期归属：利用率使用已完成计划服务分钟数除以已发布排班扣除休息和生效停班后的容量；价格仅汇总已完成预约快照并持续标记“非实收金额”；取消、爽约、服务终止和九十天复访均按工单定义独立计算。
- 固定数据测试覆盖精确公式、上海日期边界、空周期、局部失败、周期失败后的旧结果来源标记、跨响应版本失配及无权限；管理端全量测试、API 全量测试、构建和真实 PostgreSQL 浏览器流程均通过。
